# Overview

The Simple Function Points (SFP) Measurement Engine is a deterministic SpecMetrics plugin responsible for computing the functional size of a software system using the **Simple Function Points** methodology.

Unlike the traditional IFPUG Function Point Analysis (FPA), SFP intentionally reduces measurement complexity by using a simplified functional model composed of only two measurable component types.

The plugin consumes the Canonical Functional Model (CFM) generated by previous semantic pipeline stages and produces an explainable, reproducible functional size measurement suitable for estimation, benchmarking, portfolio analysis and project governance.

The plugin is completely deterministic and performs no semantic inference.

---

# Objectives

The Measurement Engine SHALL:

- produce repeatable SFP measurements;
- require no manual DET/RET/FTR counting;
- preserve full explainability;
- integrate with Rule Packs;
- operate as a Kernel Plugin;
- support organizational extensions without modifying the engine.

# User Scenarios & Testing

## User Story 1 — Automatic SFP Measurement (Priority: P1)

A software estimator executes:

```

```

The engine automatically identifies measurable functional components from the Canonical Functional Model and produces the total Simple Function Point size.

### Acceptance

- measurement completes without manual interaction;
- every counted component appears in the report;
- total SFP is deterministic.

- applied rules;
- measured component;
- individual contribution.

## User Story 3 — Rule Pack Customization (Priority: P2)

The engine applies the policies before producing the final result.

# Measurement Model

Unlike traditional Function Points, SFP measures only two functional component categories.

## Logical Function

Represents persistent business information recognized by users.

The engine SHALL identify logical information groups contained in the CFM.

Each identified Logical Function becomes one measurable component.

---

## Functional Process

Represents a complete user-recognizable business process.

The engine SHALL identify Elementary Processes contained in the CFM.

Each process becomes one measurable component.

---

# Functional Identification

### FR-011

The engine SHALL identify Logical Functions from CFM Data Groups via node type/attribute matching on the CFM schema (`node_type`, `semantic_type`).

---

### FR-012

Logical Functions SHALL represent user-recognizable business information.

---

### FR-013

Logical Functions SHALL ignore implementation details.

---

### FR-014

The engine SHALL identify Functional Processes via CFM node type/attribute matching (`node_type == "elementary_process"` or equivalent semantic marker).

---

### FR-015

Each Functional Process SHALL represent one complete business interaction.

---

### FR-016

Partial business operations SHALL NOT be measured independently.

---

### FR-017

Duplicate Functional Processes SHALL be merged by CFM node ID and content fingerprint (SHA-256 of `document_id`, `section_id`, `text`, `semantic_type`).

---

### FR-018

Duplicate Logical Functions SHALL be merged by CFM node ID and content fingerprint (SHA-256 of `document_id`, `section_id`, `text`, `semantic_type`).

---

# Assumptions

- The Canonical Functional Model has already been validated.
- Rule Packs have been resolved before measurement.
- Export plugins consume Measurement Results.
- Semantic extraction accuracy directly affects measurement quality.
- SFP is treated as an independent measurement methodology plugin, separate from FPA, SNAP, COSMIC or NESMA.

---

# Implementation Notes

The SFP Measurement Engine intentionally minimizes measurement complexity by relying on a reduced set of functional concepts while preserving deterministic sizing and full traceability. Within SpecMetrics, the plugin should share the same infrastructure as other measurement engines (FPA, COSMIC, SNAP, etc.), differing primarily in its identification rules and measurement algorithm. The Kernel, Rule Pack mechanism, explainability model, pipeline integration, event contracts and output model remain common across all measurement plugins, enabling organizations to execute multiple sizing methodologies over the same Canonical Functional Model and compare their results consistently.

> **Note:** This specification intentionally defines the **plugin architecture, contracts, deterministic behavior, explainability model, and integration requirements** for a SFP measurement engine. It does not reproduce the proprietary counting rules, scoring tables, or detailed assessment procedures defined in the official SFP methodology. Implementations intended to claim conformance with SFP should use the licensed specification published by IFPUG.
